# VK Tech Presentation AI

Сервис принимает неизвестный PPTX-шаблон и контент-пакет, формирует единый план
содержания, создаёт три кандидата для каждого слайда и автоматически собирает из
них одну презентацию. В редакторе можно сравнить кандидатов по миниатюрам, выбрать
другую компоновку или перегенерировать отдельный слайд. Выбор компоновки обновляет
превью сразу; PPTX, PDF и HTML пересобираются один раз при скачивании. Скачивается
одна актуальная версия презентации.

Три варианта различаются по информационной плотности. `Крупно и кратко` использует
крупный кегль и минимум объектов, `Сбалансированно` добавляет опорные блоки,
`Подробно` показывает до трёх деталей более компактным кеглем. Это реализует
свободно выбираемую ось различий из ТЗ через плотность контента и композицию.
Модель формулирует три самостоятельные законченные версии одной мысли: короткую,
сбалансированную и подробную. Сервис не обрезает текст по числу символов и не
добавляет многоточие. Планировщик очищает служебные заголовки источника, закрепляет
за каждым слайдом отличительные термины и отклоняет изменение чисел, границ и
направления оптимизации. Для нативных схем отдельно создаются 2–3 короткие подписи.

## Текущее состояние

Работает полный программный путь: безопасный импорт PPTX, Design IR и Content IR,
планирование через Polza API, классификация и структурирование
слайдов, три внутренние Scene IR, автоматическая оценка и сборка выбранной Scene IR,
нативные текст, таблицы, графики и редактируемые схемы из фигур, экспорты, превью,
детерминированный и контекстуальный аудит, покадровый выбор и перегенерация.
Планировщик автоматически выбирает, где нужна генерируемая иллюстрация, где лучше
редактируемая схема, диаграмма или таблица, а где визуал не добавляет смысла.
Для иллюстрации создаются три широких кандидата. Визуальная модель оценивает их
соответствие смыслу, естественность и композицию; если все кандидаты слабые, сервис
автоматически заменяет изображение редактируемой схемой. В редакторе доступны
режимы «Авто», «Без визуала», «Схема» и «Иллюстрация», а принятые кандидаты можно
переключать по миниатюрам.
Редактируемые схемы выбираются по смыслу слайда: доступны слои, сравнение,
fork/join, дерево редукции, Work/Span, уровневый DAG, доступ к общей памяти,
формула и планировщик. Концептуальные переходы сервис показывает редактируемыми
схемами, а генерацию изображений оставляет для сцен, где важен физический или
ситуационный образ. Ограничения реальной PRAM-системы показаны отдельной нативной
схемой «идеальная модель → кэши, межсоединение и память».
Графы строятся в два этапа: модель задаёт вершины и связи, а детерминированный
движок рассчитывает раскладку, точки присоединения стрелок, Work, Span и
критический путь. Учебные числа помечаются отдельно, а числа из материалов
принимаются только со ссылкой на исходный факт. PPTX, PDF и HTML используют одну
смысловую структуру; фигуры и соединители в PPTX остаются редактируемыми.
Резервные схемы получают смысловые названия задач вместо букв и номеров, вершины
одной схемы используют единый размер и форму, а математические индексы выводятся
типографски (`Tₚ`, `Tₗₑᵥₑₗ`). Схемы занимают основную рабочую область во всех трёх
режимах плотности.
Редактор палитры в левой панели даёт живой предпросмотр и пересобирает все форматы
в выбранной гамме без повторного вызова текстовой модели. Внешний инференс не заменяется тестовыми ответами:
без настроенного API-ключа задача переходит в `awaiting_input`.

Контрольный прогон с синтетическим планом создаёт внутренние кандидаты и одну итоговую
колоду на каждом из трёх шаблонов.
До миграции на API был выполнен сквозной прогон на учебной презентации:
импортированы текст, заметки докладчика и встроенные изображения, после чего обе
локальные модели построили по три варианта на 12 слайдов. Подробности и ссылки на
артефакты приведены в [EVALUATION_CPP.md](EVALUATION_CPP.md).

## Быстрый запуск

Текст и vision обрабатываются через Polza API моделью `qwen/qwen3.8-27b`.
Иллюстрации создаёт `tongyi-mai/z-image` через тот же API.
Локальные модели, MLX, Apple Silicon и скачивание весов больше не нужны.

Для приложения нужны Python 3.11+, Node.js 22.13+ с npm, LibreOffice и Poppler.
На macOS `make setup` может установить системные зависимости через Homebrew.
На Debian/Ubuntu установите системные зависимости:

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv make curl libreoffice-impress poppler-utils fonts-dejavu-core
# Если Node.js установлен через nvm, активируйте его в текущем терминале:
nvm use 24
node --version
npm --version
```

Если Node.js ещё нет, установите Node.js 24 LTS с npm; для уже установленного
nvm можно выполнить `nvm install 24`. Команды `make` запускайте без `sudo`.
Версия pnpm закреплена в `frontend/package.json`: `make setup` автоматически
устанавливает её в `.tools/pnpm/` через npm. Глобальный pnpm и Corepack не нужны.
Это устраняет ошибку Corepack `Cannot find module .../pnpm/12.4.2/bin/pnpm.cjs`;
очищать глобальный кэш или переустанавливать Node.js для этого не требуется.

```bash
make setup
# Укажите POLZA_API_KEY в .env
make run
```

Для ручных команд фронтенда используйте `sh scripts/pnpm.sh run dev` или
`sh scripts/pnpm.sh run build` из корня проекта. Docker использует тот же
скрипт и ту же закреплённую версию. Разрешён install-скрипт только `esbuild`.

`make run` запускает API и worker, интерфейс доступен на
`http://127.0.0.1:8000`. Логи находятся в `.local/logs`; остановка — Ctrl+C.
Приложение автоматически читает локальный `.env`; уже заданные переменные
окружения имеют приоритет при прямом запуске Python/uvicorn.
Ключ остаётся на сервере и не передаётся браузеру.

Контейнерный запуск с PostgreSQL:

```bash
docker compose up --build
```

Для проверки связи с провайдером на синтетических данных:

```bash
make check-api
# Дополнительно проверить генерацию одной иллюстрации:
.venv/bin/python scripts/check_api.py --image
# Полный сценарий с рабочими схемами, рендером и синтетической презентацией:
.venv/bin/python scripts/check_api.py --pipeline
```

Эти проверки делают реальные платные API-запросы. Обычные тесты
`make test` используют изолированное окружение и не вызывают Polza.

## Настройка моделей

Минимальная настройка:

```dotenv
POLZA_API_KEY=<ваш-ключ>
MODEL_BASE_URL=https://polza.ai/api/v1
MODEL_NAME=qwen/qwen3.8-27b
```

Одна модель выполняет планирование, перегенерацию слайдов, содержательный
vision-аудит и оценку кандидатов иллюстраций. Gateway передаёт изображения в
base64 через Chat Completions API. По умолчанию используется JSON-режим:
полная схема Pydantic включается в инструкцию, ответ проверяется локально.
Проверки фактов и структуры сохраняются. Причина выбора режима и настройка
`MODEL_RESPONSE_FORMAT` описаны в [MODELS.md](MODELS.md).

Старые `MODEL_MODE`, `MODEL_PROFILE`, `VK_*` и MLX-параметры больше не
используются. При переносе существующего `.env` замените локальные адреса
`MODEL_BASE_URL` и `T2I_BASE_URL` адресами API из `.env.example`.
Устаревшее имя MLX-модели в `MODEL_NAME` нужно заменить на `qwen/qwen3.8-27b`.

Иллюстрации используют тот же `POLZA_API_KEY`:

```dotenv
T2I_BASE_URL=https://polza.ai/api/v1
T2I_MODEL=tongyi-mai/z-image
T2I_ASPECT_RATIO=16:9
T2I_TIMEOUT_SECONDS=180
```

Polza Media API создаёт задание; worker опрашивает его статус и скачивает
результат в локальное хранилище. Чтобы отключить новые иллюстрации, задайте
пустой `T2I_BASE_URL=`. Для отдельного OpenAI-совместимого сервиса задайте
`T2I_BASE_URL`, `T2I_API_KEY` и `T2I_MODEL`; он должен возвращать base64.
Ключ Polza не подставляется автоматически для другого домена.

`MODEL_REASONING_ENABLED=0` отключает reasoning по умолчанию.
Лимиты ответа задаются переменными `MODEL_MAX_TOKENS_<ROLE>`.
`MODEL_TRUST_ENV=1` включает использование стандартных HTTP(S)-прокси
из окружения; по умолчанию соединение прямое.
`MODEL_CACHE=0` отключает прикладной кэш для измерений.
Ошибки авторизации, баланса, доступности API и обрезанные ответы переводят
задание в `awaiting_input` с понятной причиной.

Пути к рендерерам можно переопределить переменными `SOFFICE` и `PDFTOPPM`.
`FONT_DIRS` содержит разделённые системным символом пути к TTF/OTF.
Подробности конфигурации и ссылки на документацию: [MODELS.md](MODELS.md).

## Формат шаблона

В PPTX нужен хотя бы один слайд с областями заголовка и основного текста.
Поддерживаются как заполненные примеры, так и пустые текстовые заполнители
PowerPoint с оформлением, унаследованным от макета. Пустой файл или набор
только из изображений не задаёт редактируемую текстовую компоновку.
Проверка шаблона выполняется до платных запросов к моделям. При повторе задания
исходный PPTX разбирается заново; после обновления импортера загружать его ещё
раз не требуется.

## Формат контента

Поддерживаются PPTX, PDF, UTF-8 TXT/Markdown, CSV и JSON `ContentIR`. Импорт PPTX
группирует текст по исходным слайдам, отдельно сохраняет заметки докладчика и
автоматически регистрирует встроенные PNG/JPEG/WebP как assets. Вопросы,
разделители и слайды без извлекаемого текста остаются необязательными источниками,
чтобы их можно было сократить без потери фактов. До четырёх наиболее значимых
изображений передаются мультимодальному планировщику; лимит задаёт
`MODEL_MAX_SOURCE_IMAGES`. Полный Content IR остаётся в задании и отчёте, а в
контекст планирования передаются обязательные факты и компактный каталог assets;
его размер задаёт `MODEL_MAX_PLANNING_ASSETS`. PDF импортируется смысловыми
фрагментами примерно по 500–1200 символов с точной ссылкой на страницу и номер
фрагмента; наиболее близкие к брифу блоки выбираются в
ограниченный контекст планировщика. Лимиты задают `MODEL_MAX_PLANNING_CLAIMS` и
`MODEL_MAX_PLANNING_CHARS`. Презентации длиннее 12 слайдов планируются связанными
блоками максимум по шесть слайдов. Каждому слайду заранее назначается отдельный
диапазон исходных фактов; повтор заголовка или главной мысли отклоняется до верстки.
CSV должен иметь категории в первом столбце,
названия рядов в первой строке и числовые значения в остальных ячейках. Для
отсутствующего корпоративного шрифта генератор использует `FONT_FALLBACK`
(по умолчанию Arial) и проверяет размеры текста по установленному файлу шрифта.
Для сложного пакета используйте JSON по схеме `/openapi.json`; `source` обязателен для
каждого факта и набора данных. Изображения сначала загружаются через `/api/assets`,
после чего возвращённый относительный `path` можно указать в `ContentIR.assets`.
Для изображений внутри PPTX этот шаг выполняется автоматически.

Реальный приёмочный прогон PPTX-контента запускается так:

```bash
.venv/bin/python scripts/evaluate_pptx.py content.pptx template.pptx --output output/evaluation-api
```

## Проверки

```bash
.venv/bin/python -m pytest -q
.venv/bin/python scripts/verify_templates.py /path/to/templates --output output/smoke
cd frontend && pnpm run build
```

`verify_templates.py` использует подписанный синтетический fixture и не вызывает
модель. Он проверяет девять PPTX, PDF, HTML, Scene IR и отчётов аудита. PostgreSQL
проверяется при наличии `TEST_DATABASE_URL`. Результаты smoke-прогона исключены
из Git.

## Ограничения

- Серверный рендер LibreOffice может отличаться от PowerPoint при отсутствии
  корпоративных шрифтов. В предоставленных материалах отдельных файлов шрифтов
  нет: используются системные шрифты и настройки PPTX, а аудит возвращает
  `unknown` при невозможности подтвердить метрики.
- Контекстуальный аудит зависит от vision-возможностей API-модели. Исторические
  оценки локальных Qwen/Ministral не характеризуют текущий Qwen3.8-27B.
- Схемы состоят из обычных редактируемых фигур PowerPoint. Это даёт одинаковый
  размер карточек и текста в PowerPoint и LibreOffice.
- Поддержка шаблонов PDF и изображений остаётся расширением. Основной адаптер — PPTX.
- Публичный доступ требует внешней аутентификации, TLS, антивирусной проверки и
  объектного хранилища; текущая конфигурация слушает только localhost.
